Prompt para el Sistema de venta de entradas 

Descripción general:

Desarrollar un “Sistema de Venta de Entradas” para Recitales. Para el mismo se deben utilizar conceptos de Programación concurrente (threads, procesos, sincronización, locks, colas, etc.). No es necesario que se usen todos los conceptos, solo los necesarios para esta solución. En esta solución no se deben utilizar sistemas externos como por ejemplo AWS, sino que los mecanismos utilizados deben ser propio del Sistema Operativo. 

Alcance del sistema 

El sistema de venta de entradas tiene que permitir a los usuarios ver todos los asientos disponibles para un determinado recital, para poder seleccionarlos y reservarlos. Hay que tomar en cuenta que los asientos pueden estar DISPONIBLES, RESERVADOS TEMPORALMENTE o VENDIDO.  

El manejo de la concurrencia en este sistema es crítico y vital. Puede haber cientos o miles de usuarios intentando reservar entradas al mismo tiempo y pueden querer reservar los mismos asientos. 

Cuando un usuario selecciona un asiento, el sistema se lo reserva por 5 MINUTOS (parámetro configurable), momento en que pasa al estado RESERVADO TEMPORALMENTE. Si pasa el tiempo y no se confirma (vende) la reserva, el sistema “libera” el asiento disponibilizándolo para otros usuarios. Mientras esté temporalmente reservado, a todos los usuarios que lo estaban visualizando como disponible tienen que verlo marcado con el nuevo estado, sin necesidad de actualizar la página. Lo mismo cuando se libera el asiento.  

Lenguaje de Programación: Python 3.14

Plataforma dónde se ejecutará: GNU Linux 

Agente de IA utilizado para la implementación: Claude Code (Haiku 4.5, Sonnet 4.6 y Opus 4.7) 

Requisitos específicos:

- El sistema debe ser frontend con un backend al cual realizar consultas. Es el backend quien debe tener toda la lógica de negocio. 

- El sistema debe funcionar todo en un mismo servidor. 

- El sistema debe utilizar una base de datos PostgreSQL versión 18. 

- El sistema debe tener un login básico y autenticarse contra la DB, con información mínima de cada usuario. 

- El sistema tiene que manejar la concurrencia para la selección de asientos mediante la base de datos. Ejemplo: una query que actualice el estado del asiento únicamente si ese asiento está disponible (WHERE = ‘available). De esta manera, ya que las queries en la base de datos me garantizan atomicidad, estaría resolviendo el problema de la race condition. 

- El sistema debe soportar demanda concurrente, considerar de cientos a miles de usuarios en el mismo momento, considerando también optimización de memoria e hilos. 

- El sistema debe evitar deadlocks y problemas de concurrencia (acceso simultáneo al mismo recurso cuando ya está siendo tomado por otro recurso). 

- El sistema debe utilizar conceptos como Threads, Procesos, Sincronización, Locks, Colas, etc. (no es necesario usar todos, solo los que mejor se adecuen a la solución) garantizando un correcto uso de recursos.  

- El sistema debe gestionar lo que es la selección de asientos únicamente y poder luego continuar con el pago. 

- Los clientes deben poder seleccionar uno o más asientos al momento de comprar la entrada. 

- El acceso será concurrente, es decir, puede ocurrir que dos personas quieran seleccionar el mismo asiento al mismo tiempo. Solo uno debe poder seleccionarlo, al otro se le debe mostrar un mensaje en el frontend indicándole que fue reservado. 

- El sistema debe permitir sacar entradas en únicamente 3 secciones: Campo, Platea y Platea VIP. 

- El sistema debe validar la disponibilidad de asientos seleccionados al momento de iniciar el proceso de compra. 

- El sistema debe “reservar” temporalmente los asientos seleccionados por el cliente hasta que pase el tiempo de compra o se cancele la compra (Botón Cancelar). 

- Ya que el sistema debe estar enfocado en la resolución de la concurrencia en la reserva y venta de entradas, el alta/baja/modificación de recitales no es prioritario para este sistema. Por lo tanto, se deberá la carga de todos los asientos que disponibiliza un recital por archivos JSON, siendo el sistema el responsable de parsear y manejar los asientos a partir de esos datos. Esto con el fin de simplificar el manejo de los recitales. Se requiere crear varios archivos de prueba, para realizar la carga. Los usuarios, en el front, una vez logueados deben seleccionar el recital a asistir de un listado para visualizar los asientos disponibles. 

- En el frontend, los colores de los asientos disponibles deben ser de color verde y se debe actualizar en tiempo real los asientos reservados en color rojo. 

- El sistema debe escribir un log cada vez que se detecte una race condition. Ejemplo: el usuario A quiso reservar el asiento C1 al mismo tiempo que el usuario B. En ese caso la base de datos maneja esa race condition ya que sus sentencias son atómicas y si un usuario B obtiene que se modificaron 0 filas, eso significaría que el asiento está reservado por el usuario A en este caso. Esto debe ser informado en un log, avisando que se detectó la condición de carrera y que solo uno de los dos usuarios obtuvo el asiento.  

- Se debe generar un batch o casos de prueba para evaluar correctamente los casos de race condition. 


Restricciones: 

- El pago debe simularse con stubs, permitiendo avanzar en la reserva del asiento sin realizar ninguna operación real contra algún sistema externo, de forma de poder implementar el servicio de pagos a futuro. 

- La selección de asientos en la interfaz (frontend) no garantiza su disponibilidad. 

- Los asientos seleccionados por el cliente se liberan una vez que al cliente le pasan los 10 minutos de tiempo de compra. 

- Al momento de que un cliente selecciona un asiento, el mismo debe actualizarse para todos los demás en la interfaz (frontend), quedándose así bloqueada para todos los demás. 

- Si un cliente A seleccionó un asiento y al mismo tiempo (o 1 segundo después) otro cliente B también lo seleccionó sin haberse actualizado la interfaz (frontend), el cliente B debería ver un mensaje de “ese asiento ya fue seleccionado” por más que el asiento no esté marcado en el frontend como reservado. 

- Los recursos del backend/lógica de negocio deben utilizar mecanismos de sistema operativo como Threads, Procesos, Sincronización, Locks, Colas, etc.
